# tapmon

背面を 2 回 / 3 回叩いて、戻る・ホーム・再生停止などを実行する。Pixel の
「背面タップ」や iPhone の「背面タップ」を、加速度センサーだけで他の端末に持ってくる。

- Android 9 (API 28) 以降。試したのは Xperia XQ-FS44 / Android 16
- 要求する権限は `VIBRATE` と `WAKE_LOCK` の二つだけ（どちらも normal、ダイアログは出ない）
- 外部ライブラリなし。APK は **45 KB**
- 常駐するが、電池を使うのは**画面が点いている間だけ**

```
tapmon.apk   ← これを端末に入れる
```

## 加速度だけでどう「叩き」を見分けるか

学習モデルは使わない。指で叩いた衝撃には、他の動きと分けられる素性が三つある。

| 素性 | 内容 | 弾けるもの |
|---|---|---|
| 向き | 背面を叩くと端末は画面の側へ押される。Android の座標系で **+Z** | 画面側を叩く、横揺れ |
| 短さ | 衝撃は数十ミリ秒で終わる。長く続く力は叩きではない | 持ち上げる、置く、傾ける |
| 静けさ | 揺れが続いている間はどんなしきい値でも誤検出する | 歩行、乗り物 |

この三つを通った山を「叩き」と数え、0.45 秒以内に 2 つ並べば 2 回タップ、
3 つ並べば 3 回タップとする。判定は [`TapDetector.java`](app/src/main/java/io/tapmon/TapDetector.java) に全部ある。

時間はすべて `SensorEvent#timestamp`（端末の単調増加時計）で測る。到着時刻を使うと、
センサーのまとめ配送で間隔が潰れて測れなくなる。

## 実機で測ったこと

判定の定数は勘で置かず、**実機で記録した波形から決めた**。計測は tapmon 自身に
一時的な出力を足して行い（重力を抜いた Z 成分を 743ms ぶんログに流す）、
背面を 2 回叩く動作を 22 本記録した。波形は `TapDetector` に再生して確かめてある。

### 読み取りの実際

| 項目 | 要求 | 実際 |
|---|---|---|
| サンプル間隔 | 5000µs (200Hz) | **4.65ms = 215Hz** |
| まとめ配送 | 50000µs (50ms) | `result=OK`（FIFO 10000 件の端末） |
| 追加権限 | — | 不要（200Hz を超えなければ `HIGH_SAMPLING_RATE_SENSORS` は要らない） |

センサーは STMicro LSM6DSO、最大 416Hz、**non-wakeup**。画面が消えている間は
どのみち安定して届かない型なので、「消えたら外す」で失うものがない。

### 叩きの波形

```
… -0.40 -0.39 -0.35 -0.25 -0.09  1.26  4.41  4.46  4.00  3.46  3.19  2.77  2.19  1.48  0.77  0.19 …
                                   ↑ 4ms で頂点。そこから 20〜45ms かけて消える
```

| 測ったもの | 結果 |
|---|---|
| 山の高さ（叩き 36 回） | 最小 **3.8** / 中央 **5.7** / 最大 8.8 |
| 山が続く時間 | 最大 **46ms**（上限は 70ms に置いた。余裕あり） |
| 端末を持ち替えるなど普通の扱いで立つ山 | **1〜3**（叩きの下限 3.8 と重ならない） |
| 2 回叩きの間隔（16 組） | 214〜507ms、中央 **349ms** |

### この計測で直した二つの間違い

**1. しきい値 4.5 は高すぎた。** 最初は「標準 = 4.5 m/s²」と置いていたが、
実測した山の最小は 3.8、中央でも 5.7 しかない。22 本を再生すると 4.5 では 11 本しか
成立しなかった。段を `{6.5, 4.5, 3.2, 2.6, 2.0}` に取り直し、**標準を 3.2** にした。

| 感度 | しきい値 | 22 本中、2 回タップが成立した本数 |
|---|---|---|
| とても鈍い | 6.5 | 0 |
| 鈍い | 4.5 | 10 |
| **標準** | **3.2** | **15** |
| 敏感 | 2.6 | 15 |
| とても敏感 | 2.0 | 17（ただし机に置いた衝撃まで 2 回と数え始める） |

とても敏感にすれば 17 本まで伸びるが、そこでは「端末を置いた」だけの衝撃
（山の高さ 12.9 と 34.4 が記録に残っている）も 2 回タップと数えてしまう。
だから既定は標準に置いてある。

**2. 窓 350ms は狭すぎた。** 人が 2 回叩く間隔は思ったより遅く、中央値が 349ms。
350ms の窓では **16 組中 7 組が落ちる**。450ms に広げると落ちるのは 1 組だけ。

| 窓 | 窓から落ちる組 |
|---|---|
| 350ms | 7 / 16 |
| **450ms** | **1 / 16** |

これ以上広げないのは、3 回タップを使うときの待ちがそのまま延びるのと、
無関係な 2 つの衝撃が偶然 1 組と見なされる危険が増えるため。

### 一度も反応しなかった欠陥

最初に書いた `TapDetector` は、**どの叩きにも一切反応しなかった**。原因は
不応期の起点を `Long.MIN_VALUE` で初期化していたこと。

```java
private long lastCommitNs = Long.MIN_VALUE;
…
if (tNs - lastCommitNs < REFRACTORY_NS) return;   // 引き算が桁あふれして常に負
```

`tNs`（1e13 程度）から `Long.MIN_VALUE` を引くと `long` が一周して負になる。
つまり「ずっと不応期の最中」と判定され、山を一つも数えられない。実機に入れる前に
波形を流して気づいた。いまは最初のサンプルで `lastCommitNs = tNs - REFRACTORY_NS`
と置いている。

### 省電力 (100Hz) の代償

215Hz の記録を 1 つおきに読んで 108Hz 相当にすると、山の高さはこう変わる。

| 読み取り | 山の頂点（最小 / 中央 / 最大） | 22 本中の成立数（標準） |
|---|---|---|
| 215Hz | 3.8 / 5.7 / 34.4 | 15 |
| 108Hz | **2.1** / 4.7 / 34.4 | 12 |
| 54Hz | 0.1 / 3.8 / 34.4 | （使いものにならない） |

叩きは 4ms で頂点に達するので、粗く読むと頂点そのものを踏み外す。
省電力は「2 割ほど取りこぼす」と承知の上で使うもの。既定は切ってある。

## 要求する権限: 振動だけ

```
$ aapt2 dump permissions tapmon.apk
package: io.tapmon
uses-permission: name='android.permission.VIBRATE'
uses-permission: name='android.permission.WAKE_LOCK'
```

`WAKE_LOCK` は「画面が消えている間も見張る」ためだけに使う（[画面が消えている間](#画面が消えている間)）。
既定では音が鳴っている間しか握らない。設定を切れば一度も握らない。

`VIBRATE` は叩きに気づいた合図に使う。保護レベルは normal で、インストール時に
自動で付き、許可を尋ねるダイアログも出ない。できることは振動だけで、そこから
何かを読み取ることはできない。設定の「タップに気づいたら振動する」を切れば
一度も使わない。**振動が要らないなら、マニフェストのこの一行を消して組み直せば
権限ゼロになる**。

要りそうで要らないもの:

| やること | 使うもの | 権限 |
|---|---|---|
| 加速度を読む | `SensorManager` | 不要（200Hz を超えなければ） |
| 戻る・ホーム・通知など | `performGlobalAction` | アクセシビリティの有効化のみ |
| 再生停止・曲送り | `AudioManager#dispatchMediaKeyEvent` | 不要 |
| ライト | `CameraManager#setTorchMode` | 不要（`CAMERA` は要らない） |
| アプリを起動 | `<queries>` で MAIN/LAUNCHER だけ見る | `QUERY_ALL_PACKAGES` は要求しない |
| 常駐 | アクセシビリティサービス | 前面サービスも通知も不要 |
| 画面消灯中の見張り | `PARTIAL_WAKE_LOCK` | `WAKE_LOCK`（normal。使うのは設定を入れたときだけ） |

インターネットも位置情報もストレージも通知も使わない。

アクセシビリティサービスの構成も絞ってある。

| 設定 | 値 | 意味 |
|---|---|---|
| `accessibilityEventTypes` | 指定なし | 画面上のイベントを一切受け取らない（※） |
| `canRetrieveWindowContent` | `false` | 画面の内容を読まない |
| `canRequestFilterKeyEvents` | 指定なし | キーも横取りしない |

tapmon がシステムに頼むのは `performGlobalAction` を実行させてもらうことだけ。

※ ただし「登録したアプリを使っていたとき」を選んだときだけは、`setServiceInfo` で
`typeWindowStateChanged` を動的に開ける。届くのは「どの窓が前に来たか」で、見るのは
パッケージ名だけ。`canRetrieveWindowContent=false` は変えないので、画面の内容は
そもそも読めない。登録を空に戻せば受け取りも止まる。

## なぜアクセシビリティサービスなのか

「戻る」「ホーム」「通知パネル」を他のアプリの上から実行する道が、非 root では
これしかない。副産物として、システムがサービスを束縛して常駐させてくれるので、
**常駐のためのフォアグラウンドサービスも通知も自動起動の権限も要らない**。
端末を再起動してもシステムが自動で繋ぎ直す。

## 電池

画面が点いている間しかセンサーを開かない。これが一番効く。

```
17:42:15 + accelerometer  samplingPeriod=5000us batchingPeriod=50000us   ← 画面 ON で取得
17:42:29 - accelerometer                                                 ← 画面 OFF で解除
17:42:30 + accelerometer  samplingPeriod=5000us batchingPeriod=50000us   ← 画面 ON で再取得
```

（`adb shell dumpsys sensorservice` の実機の記録。画面の開閉に合わせて付け外しできている）

そのうえで、

1. **画面が消えている間の消費はない。** センサーを外し、タイマーも持たない。
   常駐はしているが何もしない。
2. **画面が点いている間は CPU がもともと起きている**ので、加速度計を足す分の負担は小さい。
3. **まとめ配送**（`maxReportLatencyUs = 50ms`）でセンサー側に溜めてもらい、CPU を
   起こす回数を約 1/10 に減らす。溜めても 1 サンプルごとの時刻は保たれるので判定は鈍らない。
   FIFO の無い端末では黙って無視される。
4. **判定は専用スレッド**で走らせ、UI スレッドを毎秒何十回も起こさない。
5. **外部ライブラリを読まない。** 起動時に広げる dex が小さいほど速くて軽い（45 KB）。

**実際に何 % 減るかは測っていない。** 端末とセンサーハブの作りで変わる。
設定 → 電池 → 電池の使用量で tapmon を見れば確かめられる。減りが気になるなら、
省電力（100Hz）に落とすか、使わない間は設定画面のスイッチで切る。

## 画面が消えている間

画面が消えている間も背面タップを拾いたい（音楽を止める、など）場合、この端末では
**CPU を寝かせない**より他に道がない。センサーの一覧を見ればそれが分かる。

```
0x0000000b) lsm6dso Accelerometer Non-wakeup      ← 加速度計はこれだけ。起床できる版がない
0x000000ac) sns_smd Wakeup  (significant_motion)  ← 起床できるのは「大きな動き」系だけ
0x000000fc) pickup_gated Wakeup (pick_up_gesture)
0x0000012e) motion_detect_wakeup
```

起床できるセンサーはどれも「歩き出した」「持ち上げた」を数秒の尺度で見るもので、
数十ミリ秒の叩きは見分けられない。加速度計に起床できる版があれば、センサー側で
溜めておいて CPU を起こしてもらえるのだが、それが無い。

そこで、**どういうときに見張るか**を選べるようにしてある。

| 選択肢 | 何が起きるか | 電池 |
|---|---|---|
| しない | 画面が消えたらセンサーを外す | 消灯中の消費はゼロ |
| **音が鳴っている間だけ**（既定） | 鳴っている間と、鳴り止んでから 5 分 | 安い（下記） |
| 登録したアプリを使っていたとき | 画面を消す直前に前面だったアプリが登録済みなら見張る（30 分で打ち切り） | そのアプリのときだけ |
| その両方 | どちらかに当てはまれば見張る | |
| ずっと | 消灯中ずっと CPU が起きたまま | 高い |

「鳴り止んでから 5 分」を足してあるのは、**叩いて止めたあと、叩いて鳴らし直せる**ように。
鳴っている間しか見張らないと、止めた瞬間に見張りも終わるので鳴らし直せない。
「登録したアプリ」の 30 分の打ち切りは、何も起きないまま一晩中 CPU を起こさないため。
タップを見つけるか音が鳴れば、そこから数え直す。

### 音が鳴っている間だけ

そこが一番安い場所だから既定にしてある。音を鳴らしている間は音声処理のために CPU が
起きていることが多く、そこに加速度計を足す負担は小さい（ただし DSP に流し込む
再生の仕方をしている端末では、CPU が寝られるはずのところを起こすことになる）。

鳴り始めと鳴り終わりは `AudioManager#registerAudioPlaybackCallback` で教えてもらう。
権限は要らない。**止めたあとは音が鳴っていないので、叩いて鳴らし直すことはできない。**
鳴らし直しもしたいなら、次の「登録したアプリ」か「ずっと」を選ぶ。

### 登録したアプリを使っていたとき

前面にあるアプリは、アクセシビリティの `TYPE_WINDOW_STATE_CHANGED` から
**パッケージ名だけ**を受け取って覚えておく。追加の権限は要らない
（`PACKAGE_USAGE_STATS` も `QUERY_ALL_PACKAGES` も要求しない）。

**この受け取りは、アプリを登録したときにだけ動的に開ける。** 使わない限り tapmon は
画面上のイベントを一つも受け取らない。既定の状態を `dumpsys accessibility` で見ると
こうなっている。

```
Service[label=tapmon, feedbackType[FEEDBACK_GENERIC], capabilities=0, eventTypes=, …]
                                                      ↑ 何も持たない   ↑ 何も受け取らない
```

判じ方は単純で、**画面を消す直前に前面だったアプリが登録済みかどうか**だけを見る。
音楽アプリを開いて画面を消す、という流れならこれで足りる。別のアプリに切り替えてから
画面を消した場合は見張らない。

### 消えている画面で効く動作

| 動作 | 消灯中 | 備考 |
|---|---|---|
| 再生 / 一時停止・次の曲・前の曲 | 効く | メディアキーはそのまま届く |
| ライト | 効く | |
| アプリを起動 | 効く | 先に画面を点ける（`SCREEN_BRIGHT_WAKE_LOCK`、3 秒で自動的に離す）。端末がロックされていればロック画面が出る |
| 戻る・ホーム・履歴など | 効かない | 画面が点いていないと意味がない |

### 実機で確かめた動き

消灯中・無音なら、センサーもウェイクロックも握らない。

```
18:04:42 - accelerometer          ← 画面 OFF・無音 → センサーを外す
                                  （tapmon のウェイクロックは握っていない）
18:04:45 + accelerometer          ← 画面 ON で再取得
```

消灯中に音が鳴っていれば握り、叩けば効く。

```
18:23:03  ACQ tapmon:screen-off (partial)      ← 画面 OFF・再生中 → CPU を起こす
          I tapmon: 画面消灯中の見張りを始めました
          （加速度は 4.65ms 間隔で届き続けている）
18:25:16  I tapmon: 2 回タップ (山の高さ 12.1 / しきい値 3.2)
          → 鳴っているプレイヤー 1 → 0（止まった）
```

### 握りっぱなしになっていた不具合

上の試験で、**音楽を止めたあともウェイクロックを離していない**ことが分かった。

```
PARTIAL_WAKE_LOCK 'tapmon:screen-off' ACQ=-2m56s637ms LONG (uid=10542)
                                                      ↑ システムが「長すぎる」と印を付けた
```

解放を `registerAudioPlaybackCallback` の通知だけに頼っていたのが原因。
`AudioManager#isMusicActive()` は**鳴り止んだ直後にもまだ true を返すことがある**ので、
通知の瞬間に判じると「まだ鳴っている」と読む。そのあと通知はもう来ないので、
画面が点くまで握ったままになる。一晩画面を消していれば、一晩 CPU が起きたままになる。

いまは、握っている間だけ 30 秒ごとに自分で見直す。通知は「早く気づくため」の手がかりで、
握りを解く判断はこの見直しが持つ。

## インストール

1. `tapmon.apk` を端末に転送して開く（または `adb install tapmon.apk`）
2. **Android 13 以降はここで一手間要る。** ストア以外から入れたアプリは
   アクセシビリティの項目が灰色で押せない（「制限付き設定」）。
   設定 → アプリ → tapmon → 右上の **⋮** → **制限付き設定を許可** を押してから進む
3. tapmon を開いて「アクセシビリティ設定を開く」→ インストール済みアプリ → tapmon → オン
4. 「感度」の欄を見ながら背面を叩き、数字が増えるのを確かめる

**アプリを入れ直すと、アクセシビリティの有効化は外れる。** 更新のたびに 3 をやり直すこと
（実機で確認済み。`enabled_accessibility_services` から消える）。

## 設定画面でできること

- **割り当て** — 2 回タップ / 3 回タップに動作を割り当てる
- **感度** — 5 段。いま何が起きているかを数字で出す
- **誤作動を防ぐ** — 揺れが続く間は反応しない（既定でオン）
- **電池** — 省電力（100Hz）、振動の合図
- **状態** — アクセシビリティでの有効化、センサー名、見張り中かどうか

感度の欄は調整台を兼ねている。**この画面を開いている間、tapmon は叩きを数えるだけで
動作は実行しない**（合わせている最中に「戻る」が飛んで画面が消えるのを防ぐため）。
出る数字は四つ。

| 表示 | 読み方 |
|---|---|
| 叩きと数えた山 | 増えないなら感度を上げる。勝手に増えるなら下げる |
| 弾いた山の高さ | 惜しいところで届かなかった衝撃。しきい値のすぐ下なら一段上げれば届く |
| いまの揺れ | 2.0 を超えている間は「揺れ止め」が働いて反応しない |
| しきい値 | いまの感度の数字 |

ケースを付けると衝撃が弱まる。既定値を信じるより、ここで測って決めた方が早い。

## 割り当てられる動作

| 動作 | 実現 | 備考 |
|---|---|---|
| 戻る / ホーム / 最近のアプリ | `performGlobalAction` | |
| 通知パネル / クイック設定 | 同上 | |
| スクリーンショット | 同上 | Android 11 以降のみ一覧に出る |
| 画面をロック / 電源メニュー | 同上 | |
| 再生 / 一時停止・次の曲・前の曲 | `dispatchMediaKeyEvent` | 宛先は Android が選ぶ |
| ライト | `setTorchMode` | 他のアプリがカメラを使っていると断られる |
| アプリを起動 | `startActivity` | ホーム画面に並ぶアプリから選ぶ |

## はじめから無視しているもの

- **通話中・呼び出し中**（`AudioManager#getMode() != MODE_NORMAL`）。事故になる
- **画面が消えている間**（既定では音が鳴っている間だけ見張る。[上記](#画面が消えている間)）
- **画面側を叩いた衝撃、横揺れ**。向きが違う（頂点が Z に寄っていること、を条件にしている）
- **長く続く力**。持ち上げる・置く・傾けるは、叩きにしては長すぎる
- **揺れが続いている間**（設定で切れる）

## 確かめたこと / 確かめていないこと

**実機 (Xperia XQ-FS44 / Android 16) で確かめた**

- **背面を 2 回叩いて「戻る」が実際に効く。** 検出からシステムが動くまで 11ms

  ```
  17:47:29.917  tapmon : 2 回タップ (山の高さ 3.5 / しきい値 3.2)
  17:47:29.928  ActivityTaskManager: moveTaskToBack …  ← 11ms 後
  ```

- 連続して叩いた 17 回すべてを検出。山の高さは 3.4〜7.8（記録した 22 本の
  3.8〜8.8 とよく合う）。例外もエラーも出ていない
- アクセシビリティサービスが繋がり、200Hz + 50ms まとめ配送の要求が `result=OK` で通る
- 画面 ON でセンサー取得、OFF で解除、ON で再取得
- 背面タップの波形を 22 本記録し、そこから感度と窓を決めた
- 入れ直すとアクセシビリティの有効化が外れる

**波形の再生で確かめた**（`bash tools/testbed/run.sh` で誰でも再現できる）

- 2 回 / 3 回の数え分け、3 回タップ無効時は 2 回目で即実行
- 間隔が空いた 2 回、1 回だけ、画面側を叩く、横から叩く、持ち上げて置く → 反応しない
- 歩行の揺れ（揺れ止め入で反応せず、切ると反応する）
- まとめ配送（10 サンプルずつ届く場合）でも 2 回 / 3 回を取り違えない

**まだ実機で確かめていない**

- 実際の電池の減り方（数字を出していない）
- 歩行中・ポケットの中での誤作動の頻度
- ライトの切り替え（他社端末でカメラの扱いが違う可能性）
- アプリの起動（Android 10 以降の「背後からの起動制限」に当たる端末があるかもしれない）
- Android 9〜15 での動作（minSdk は 28 に合わせてあるが、手元の実機は 16 のみ）

## ビルド

Gradle を使う道と、Android SDK の道具だけで組む道の両方がある。出来上がりは同じ。

```sh
bash tools/build.sh          # aapt2 → javac → d8 → zipalign → apksigner
# → build/tapmon.apk （ついでに tapmon.apk としてルートにも置く）
```

```sh
./gradlew assembleRelease    # app/build/outputs/apk/release/app-release.apk
```

判定を触ったら、組む前に試験台を走らせる。

```sh
bash tools/testbed/run.sh
```

- JDK 17、Android SDK（build-tools と platform は最新のものを自動で選ぶ）
- 依存ライブラリなし（AndroidX も使わない）。だから APK が 45 KB で済んでいる
- 署名鍵は `keystore/tapmon.jks`（パスワードは `keystore.properties`、有効期間 30 年）。
  **この鍵は捨てないこと。** 失うと同じアプリとして更新できなくなる

## リリース

`app/build.gradle` と `tools/build.sh` の `versionCode` / `versionName` を上げて組み直し、
`tapmon.apk` を差し替えてから、commit → push → タグ（`v0`, `v1`, … と整数を 1 つずつ）を push する。
そのあと:

```sh
bash tools/release.sh v1 "v1: 見出し" notes.md
```

GitHub Release を作り、`tapmon.apk` を添えるところまでやる。この PC には `gh` が
入っていないので、GitHub API を直接叩いている。認証は Git が使っているのと同じ
資格情報（Git Credential Manager）を借りるので、トークンを別に用意しなくてよい。
取り出したトークンは `curl` の設定ファイルに直接書くだけで、変数にも画面にも出さず、
終了時にそのファイルごと消す。

タグが GitHub 側に無ければ止まる。タグを push し忘れたまま Release を作ると、
その場でタグが生えて（コミットとずれて）後始末が面倒になるため。
